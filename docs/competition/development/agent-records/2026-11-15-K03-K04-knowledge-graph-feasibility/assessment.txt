RAG 知识图谱可行性评估
日期：2026-11-15（Asia/Shanghai）
原始需求：我想在rag模块加个知识图谱功能，评估一下可行性
范围：K03/K04 增强评估，涉及 K02 数据来源、K05 课程权限、K09 展示；没有实施产品功能。
本轮开始时 git status --short 为空。原确认方案把自动图谱排除在首版之外；本评估作为新增范围建议，不修改原需求基线。
向用户询问了图谱的主要用途。编写本评估时尚未收到回答，暂按兼顾展示和问答、教师私有库先行评估。

一、结论
技术可行。推荐先做带原文证据的课程知识关系图，再以可关闭的方式增加局部图谱检索。第一版使用现有 Spring Boot、MySQL 和 Vue Flow，不增加独立图数据库。此选型针对当前方案的小规模课程资料和有限邻接查询，不是海量图谱性能结论。
展示价值比较直接；检索质量增益尚未验证。单点定义、页码查找仍适合原检索；跨章节概念联系、多证据问答更值得试点。自动学习先修关系需要教师确认，章节顺序和术语共现不能直接证明先修或因果关系。

二、已核查的项目基础
1. RagIngestionService.publish 从有效文字/OCR 页面分块，写入文档版本、解析修订、字符范围和索引版本；可复用其结果作为抽取来源。
2. RagRetrievalService 已做 BM25、向量与 RRF 融合，向量异常有明确降级；单次范围上限为 2 万片段，当前是精确扫描。增加图谱不会自动解决这个规模上限。
3. NativeRagService.searchForOwner 先核验知识库 owner，锁定有效索引快照，查询后再次校验；RagSearchHit 带文档/片段/页码/版本。图谱证据应继续使用这个来源契约。
4. NativeRagChatService.prepare 调用当前检索，取最多 5 条来源，并限制证据文本长度。图谱召回必须在最终来源编号和上下文预算之前融合，不能把整张图塞进提示词。
5. RagAuthorizationService 存在课程文档授权读取方法，但当前上述检索仍以私有库 owner 为边界。学生图谱与问答须另接 K05 服务端有效课程/课时范围，不能把已有课程授权方法视为全链路完成。
6. 前端已有 Vue Flow、KnowledgeGraphPreview 和 student/KnowledgeGraph.vue。api/knowledgeBase.js 的 getKnowledgeGraph 明确返回 unsupported=true。旧组件的 Wiki 点击逻辑、关系端点推断和布局需要调整，不能只切换开关。
7. 旧 WeKnora 中存在图谱和预设概率图逻辑，不作为上传资料自动抽取的证据，也不恢复它作为原生链路依赖。

三、建议实现
构建路径：有效文档片段 → 非 GPT 生成模型结构化抽取 → 类型/方向/原文证据校验 → 同库实体去重与别名 → 教师审核 → 版本化发布。
查询路径：原混合检索与问题实体匹配 → 在已授权有效子图内扩展 1–2 跳 → 找回支持这些关系的原文片段 → 限量融合/排序 → 原有带引用回答。
图谱关系用于定位证据；回答事实必须由实际进入上下文的原文支持。没有图谱、无实体命中或构建失败时，继续原检索并说明状态；越权或资料换版不允许通过降级扩大范围。

建议增加概念实体、别名/提及、关系、关系证据、构建任务/图谱版本等数据结构。节点与边不能只保存一段模型总结；证据应含 kbId、documentId、documentVersion、parseRevision、indexVersion、chunkId、页码或位置、原文摘录，并记录抽取模型/提示模板/模式版本。
边与证据为一对多，删除一份资料时只撤掉其证据；最后一条有效证据消失时关系失效。实体合并、拆分和教师修订保留依据，不以模型自报 confidence 当作准确率。
现有重建过程会更换 chunkId/indexVersion，因此需明确使旧映射失效或经验证重绑；不能继续引用旧片段，也不能仅凭同名实体沿用旧证据。
图谱构建放在文档索引提交后的独立持久任务，支持幂等、取消、重试、失败与过期状态，不在上传请求/数据库事务内等待模型。图谱未就绪不阻塞原 RAG。
节点、边、描述、计数和缓存均按有效资料范围过滤；未授权资料生成的合并描述不能泄露到授权子图。第一版限制同一教师知识库内合并；跨库共享和跨课程汇总单独设计。
保留 Qwen/Qwen3-VL-Embedding-8B 与 DeepSeek-OCR。关系抽取另复用经配置的非 GPT 生成模型接口，先实测结构化输出可靠性；Embedding 和 OCR 本身不替代关系抽取。

四、方案取舍与投入估算
仅绘制预设或人工图：便于展示，但不证明资料自动建图或问答增强，不推荐作为本次功能的主要交付。
原生轻量图谱：符合现有技术栈和证据/权限机制，推荐。
完整 Microsoft GraphRAG：包含实体关系抽取、社区发现和摘要等额外流程；适合全库主题概括等需求。当前项目先做局部关系检索的接入面更小。此比较为架构判断，不是本项目实测性能排名。
Neo4j 等独立图库：后续在复杂路径、跨库大图、查询性能有测量需求时再评估；目前无需因“知识图谱”名称直接引入新服务。

以下为单名熟悉项目开发者的工作量估算，非工期承诺：
- 20–30 页真实资料抽取与关系质量试点：2–3 人日。
- 累计完成教师端可用图谱（来源查看、审核、重试、版本与权限测试）：5–8 人日，含试点。
- 在此基础上增加局部图谱问答与对照评测：再增加 3–5 人日。
- 教师图谱加问答合计约 8–13 人日；学生端依赖 K05，未计入上述范围，需按有效范围实现现状单独估算。
估算假设当前模型接口可用、教师能及时审核、不做全库社区摘要和复杂图片关系识别。实际调用费用与构建耗时需由试点记录输入/输出 token、重试和增量重建量后估算；本轮没有产生或测量抽取费用。

五、验证与决策门槛（建议，尚未执行）
故事 A：教师生成图谱并点击任一关系，能看到支持该关系的真实原文和页码。
故事 B：文档更新、删除或撤权后，旧关系证据不再进入当前图谱/问答；重复任务不重复建图。
故事 C：学生仅看到课程/课时明确授权的图谱内容；空覆盖不回退到其他库。
故事 D：跨知识点问题通过图谱补齐证据，同时保留正确引用和真实降级状态。
正式开发按 Scrum + XP，先写并确认失败的权限、来源、版本、任务重试等测试，再小步实现与回归；本轮仅评估，不制造功能红绿测试。
先冻结真实课程的单点题、跨片段多跳题、无答案题及授权变更用例。调参题与验收题分开，尽量由教师独立审定；多跳题标注全部必要来源，不能只用任一来源命中代替证据完整性。
对比 BM25、现有 HYBRID、HYBRID 加图谱；使用相同生成模型、上下文预算、语料版本，评估关系证据支持率、必要来源覆盖、答案正确性/引用支持度、无答案拒答、延迟与费用。建议试点抽查至少 100 条关系或全部不足 100 条的关系，支持率目标 ≥90%，展示/引用的来源可解析率 100%，越权和失效来源暴露为 0。样本量仅支持试点判断，不代表全量统计结论。
只有多跳题获得可解释改善、单点题未明显退步且权限/版本用例通过，才默认启用图谱检索；否则保留教师导航价值并继续改进。

六、已有结果的边界
本轮读取了 2026-10-30/31 K03 归档报告与 followup-report.json：40 条可答续验题中 HYBRID 的已标注来源 Top5 为 33/40（82.5%），BM25 为 35/40（87.5%）；归档状态 FAIL，混合检索未达到原 85% 目标。这是历史检索结果，不是本轮重跑，不是答案准确率，也不是图谱效果；题目为同源开发续验而非教师独立盲测。
图谱不能被预先宣称能修复这一差距。应保留现有检索改进工作，并将图谱作为单独可对照的增量。
