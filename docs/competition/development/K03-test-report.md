## 3. 评测协议

[题集](K03-evaluation-dataset.json)在首次模型/检索成绩前冻结，[冻结散列](K03-evaluation-freeze.json)为 `38c396f43fe79528c112af744f42649ce18d485982c1b37abd505d20e5ac03ac`。10条调参，40条可答验收和10条无答案验收。原页SHA及显式gold来源可复核，题目由开发Agent依据实际页编制，尚非教师独立审定题库。

使用原件单页副本，副本页1映射到原课件页号。可可靠直接提取页及有历史真实OCR的页纳入，其余排除并计数；不声称覆盖334页。部分历史OCR来自原页的扫描副本，当前图片散列用于绑定重放，不声称新旧输入逐字节相同。真实向量按精确文本批量预计算后复用，另有未缓存生产HTTP查询；不是模拟向量，也不是每条查询均重复发HTTP。

原参数首次执行了60题，59页/59片段进入索引。40条可答验收的HYBRID已知来源Top5仅25条；真实HTTP直连、服务故障明确降级、错维度/错模型隔离通过。该live测试在同一H2内存数据库中重建NativeRagService读取数据行，报告中旧名`persistedRestartPassed`只指此行为；不是H2磁盘重开或第二JVM重启。

原验收成绩已被开发Agent观察，根工具也意外节选过原报告中的少量逐题来源ID。后续仅用原10条tuning选择参数，预登记15组及确定性选择规则见 [调参计划](K03-retrieval-tuning-plan.json)。[续验题集](K03-evaluation-followup-dataset.json)及[散列](K03-evaluation-followup-freeze.json)在调参前另冻40条可答、10条无答案；同一批来源由开发Agent改写，属于同源开发续验，不能称教师独立盲测。原题、原失败和原成绩不覆盖。

10条调参题按计划选择`rrfK=1/candidateLimit=20`（Top5 10/10，Top1 7/10，MRR@5=0.85），生产默认及手工实例保持一致。两条固定RRF公式分母61的旧单测改为显式指定60/100，使算法断言不绑定调参后的默认值，未改期望分数来掩盖算法错误。

## 4. 真实失败与修正

1. 先写4条主接口失败测试，确认旧门槛漏掉正余弦同义候选、实际模式/稳定原因缺失、查询中换版仍返回200；实现RRF及快照复核。
2. Embedding测试确认等价URL指纹不同、响应头成功后正文停滞不受超时控制；改为规范化指纹及有界异步完整响应接收，2条转绿。
3. 读取器尾随JSON垃圾、缺修订元数据和替换存储返回越界/重复项先失败后修复；真实H2行复制失去大小写不敏感语义造成500，新增回归并规范化列名。
4. 新增V005及回归，修复重建向量把解析/分块标记改成固定旧值，以及丢失字符范围影响题图关联的问题。
5. 旧4096维测试mock没有模型名，新严格检查正确降级，因此补齐fixture身份；未放宽产品校验来迁就旧测试。
6. 首次真实模型批量失败发生于prime阶段、验收查询为0。短文本1/2/32条探针成功，但实际课程32条请求出现`0..7`重复四次，8条请求序号唯一。先用重复序号回归确认RED，再将所选模型批次收至8；没有按返回顺序擅自改号，也不宣称这是供应商所有输入的公开硬上限。
7. 第二轮因三张gold页被Symbol字体的`U+F0A8/U+F0B7`项目符号误判含数学而排除，未开始验收评分。真实DeepSeek-OCR重扫和原页核查确认是项目符号。先增加两条失败测试，再仅排除这两种已核验符号；其他未核验私用字符、求和/偏导和数学字体保护仍保留。原冻结题集未改。
8. 融合只读审查未发现RRF求和/排序bug；小语料中宽候选池会偏好弱双通道共识。手工构造NativeRagService的测试不会自动读取Spring配置，后续调参必须显式注入参数化检索器，记录真实使用参数。
9. 调参预检曾使用未经校准的“同输入批量/单条cosine必须大于0.999”开发假设，导致0条网格评分即停止。13次小诊断显示批量8条各位置最近的单条向量均是自身，最小异输入区分差距0.321298；单条重复的首片段自身cosine也仅0.990519。因此没有证据认定错位，数值一致性作为观察统计保留，不以任意绝对门槛冒充供应商协议；继续维度/有限性/归一化校验，未因此改模型、提示、生产指纹或放宽坏向量校验。
10. 前端先确认取消检索会误报空结果的RED，再增加“已停止，本次未完成”状态，重试和换库清理状态；后补重试断言未冒称额外RED。
11. 开发记录先用真实测试确认子session ID被fork继承覆盖、Windows换行导致文件实际散列不符，再固定首个真实ID并按落盘字节计散列。本轮统一重导；旧任务档案未擅自重写。一次误打印的平台元数据已由导出器占位删减，公开记录不是所有原始平台字段的完整副本。

阶段运行中的旧测试夹具缺模型身份/新缓存协议字段、一次根目录误跑Maven无POM、中文编译输出匹配错误均保留原日志，不冒称产品功能RED。`green-support.log`实际为失败，最终通过以`green-support-final.log`为准。K01撤权夹具补齐模型身份并断言两次Embedding确实被调用，使“请求途中撤权”实际执行；没有放宽授权或坏向量规则。阶段定向与最终全量重叠，不累计为额外通过项。

模型[官方说明](https://huggingface.co/Qwen/Qwen3-VL-Embedding-8B)对查询和文档默认采用相同系统指令，可选自定义检索指令；本轮没有把可选指令当作确定协议缺陷，也没有引入未核验的文本前缀。

第二JVM补验也按先失败后实现执行：父进程实际上传两页合成PDF、重建索引并关闭文件数据库，缺少探针主类时子进程真实失败；实现后通过。子进程仅允许生成查询向量，禁止重新嵌入原文，原始文件SHA和持久行内容/向量SHA均核对不变。此项补足磁盘/进程边界功能证据，不修改既有课程live报告中的旧观察。
