## 发现和修复

1. 用户填写的是 `OCR_APIKEY`、`RAG_EMBEDDING_APIKEY`，原配置只读 `*_API_KEY`。已保留原变量，将其值补入缺失的Windows用户级标准变量，同时让YAML兼容别名。优先级：角色标准变量、角色别名、`SILICONFLOW_API_KEY`。OCR/Embedding不复用通用DeepSeek密钥。
2. 已运行的桌面可能早于用户环境更新。`start-local.ps1` 现在从用户环境补读缺失的OCR/Embedding设置及超时，再加载私有文件；已有进程值继续优先，更新后需要重启后端。
3. 原Embedding代码拒绝超过2048维，真实模型默认返回4096维。已支持4096维，保留超限、维度不一致、零向量及非法数值拒绝；索引增加整数范围校验，避免大整数转换截断。
4. 4096维向量JSON超过MySQL `TEXT` 的65535字节容量。新表和SQL改为LONGTEXT；旧MySQL表仅在精确匹配 `native_rag_chunk.vector_json` 且类型为TEXT时拓宽，重复启动不重复修改。元数据连接先释放再执行DDL。相似表名/列名不会触发修改。迁移通过模拟JDBC元数据验证，未在实际MySQL执行。
5. 原OCR探针仅返回适配待实现。新增独立图片HTTP客户端，并接入管理员合成图探针；保留OCR原始文本，错误不回传供应商正文、地址、密钥或异常原因链。PDF渲染和OCR标记清理尚未接入资料解析。
6. 显式开启真实模型测试后，真实失败现在会让测试失败，不会被转为跳过。日常回归仍通过环境开关禁用付费测试。

首轮Python请求因Windows配置的本地代理TLS连接失败，没有收到HTTP响应。保留该失败记录；仅在验证程序中使用直连后全部成功，项目Java客户端也成功。没有修改系统代理。首次真实测试启动还遇到验证脚本的Maven路径解析错误，修正后通过；该失败日志同样保留。

## 人工复验

1. 在项目根目录执行 `scripts/competition/start-local.ps1` 构建并重启后端，默认使用隔离演示库。确保该进程没有残留旧密钥；Windows用户环境中的新变量会补入缺失项。
2. 按 [人工验证操作](K00-manual-verification.md) 用管理员登录；GET `/api/admin/models/status` 查看四角色。这个GET只检查配置，不缓存或代表前次付费探测结果。
3. 分别POST `/api/admin/models/generation/probe`、`planning/probe`、`embedding/probe`、`ocr/probe`，均带管理员登录凭据；确认每个响应的 `data.status` 为PASS，并检查各check，不能只看HTTP200。这些请求会再次产生模型费用。
4. Embedding检查批量探测；OCR检查合成图片探测。扫描PDF上传后自动OCR尚未接入，不能用其当前上传结果判定新图片接口是否失效。
5. 自动复验方法及变量准备见人工操作文档；普通回归执行后端 `mvn test`，真实5项需显式设置 `K00_LIVE_MODEL_CHECK=true` 后运行 `RuntimeModelLiveTest`。
